# Implementation notes

This is a fresh application; no Whatsie or other messaging-client code was imported. Dependency revisions are pinned in `package-lock.json`. README documents actual behavior and limits.

## Boundaries

- `src/shared`: validated IPC/state schemas and connector command contract.
- `src/core`: portable settings, style, search, suggestion and auto-reply decisions.
- `src/connector/dom.ts`: DOM adapter. Persistent chat identity comes from recognized peer-bearing message IDs, never display names. Opaque-ID layouts become ready after a stable selected row/title/composer; main-process conversation recognition then scopes reply and style preferences. Conflicting peers fail closed. Row/identity/composer changes invalidate suggestions. Unknown authors are not treated as verified sent messages.
- `src/preload/remote.ts`: sandboxed isolated-world integration, no bridge to the page’s main world. Emits snapshots, trusted user activity/requests, observed stickers and command acknowledgements.
- `src/main`: persistence, OS encryption/native key entry, fixed-endpoint providers, validated IPC, scheduling and sending permissions.
- `src/ui`: local React controls. Keys never cross its API.

The view preserves WhatsApp Web, its session and ordinary media workflows. WhatsApp fills the content area; local controls use a separate trusted WebContentsView shown as a left settings/library panel or a right chat-settings panel. The remote page contains only closed-shadow navigation buttons that emit trusted navigation requests. No settings API is exposed to it. Composer overlays live in a closed shadow root. Page content is untrusted and can affect suggestions; it cannot change automatic-send permissions or obtain credentials. DOM automation does not guarantee compatibility with future WhatsApp changes.

## Write and race preflight

| --- | --- | --- |
| Preferences/provider | Main-process state, published to renderer | Atomic synchronous transaction, cancelled provider work, current inheritance recomputed; remote page has no settings capability. | Style learn/edit/reset | Scoped profile / prompt / profile UI | Aggregate-only local extraction, no raw examples saved; reset cancels requests and stops observation; edited profiles preserved; unsaved examples are cleared on conversation changes before they can be retargeted |

| Sticker migration | Validated full v1 state, preserved backup, original hash-keyed WebPs | Backup is non-overwritten and durable before blobs; each blob is atomically written, fsynced, re-hashed, and directory-fsynced before the v2 manifest replacement. Failed/interrupted migration retains inline data or a complete v2 manifest; GC is skipped on errors. |

Kill switch stops new direct attempts; stale nonce results cannot affect later tickets. |

Exact image/* input excludes the photo/video decoy; unique Attach/menuitem/editor/Send/close controls required. Draft changes or caption fields fail closed. Preparation/mount/auth waits are bounded at 10 s; cancellation closes app-opened controls by X, including late editor mounts. |
| Maker Send / confirmation | Final main-process authorization after editor/destination/draft checks | State stays preparing until actual editor Send activation, then sending. Missing/unsafe editor reports editor-unavailable; uncertain click reports unconfirmed without retry. This is local DOM confirmation, not a delivery receipt. |
| Key set/remove | OS-encrypted file or process memory; UI sees presence only | Native dialog singleton; insecure/locked backend rejected; durable write before memory update; session-only entry durably clears that provider's stored key first |

| Auto permission/send | Explicit per-chat rule plus durable attempt ledger | Unseen-arrival tracking excludes reappearing history; fresh text/viewport readiness can settle; budget before dispatch; no retry; runtime takeover pause survives disk failure and requires explicit resume; local and remote user interactions pause, with explicit arming and panel closing preserved; schedule/limit patches merge with authoritative permissions and preserve runtime pauses; failed resume cannot clear the latch; two-second Send wait rechecks identity/messages/activity/draft; own insertion snapshots suppressed until acknowledgement |

Atomic file replacement flushes a writable temporary-file descriptor, as required by Windows, and fsyncs the containing directory on Linux. Windows platform execution remains unverified.

No remote database mutation API. Durable state is published only after changes; transient assistant updates omit it so typing does not repeatedly copy sticker metadata across IPC or context isolation; sticker images never enter status snapshots/deltas. The renderer reconciles sequenced updates with its initial read. Preferences use patches; local UI supplies only field-level schedule/limit patches for the open chat. Enable, disable, pause and resume are distinct permission actions; repeated enable does not resume an already-enabled paused chat. One instance owns each data directory. No billing, spending-limit or organization configuration is modified.

## Suggestion request controls

The main-owned `Assistant` has three memory-only maps and one live view slot. Its 50-entry LRU stores only `{text}` or `{dismissed: true}`, keyed by stable conversation identity, latest-message semantic content and effective output preferences/provider/model/effort/key generation. Navigation revisions and older history are excluded. Only completed incoming-last empty-composer results enter the cache; explicit own-message follow-ups remain live-only. Successful refinements of an empty offer replace cached text without retaining instructions or request objects. Relevant configuration changes expire only affected conversations; observed learning and profile metadata changes preserve fingerprints and unchanged-draft suppression. Each new observation record or effective output change receives a globally increasing configuration generation. Eviction cannot reuse an earlier fingerprint, and detached completion/backoff validation only reads existing records, without touching the observation LRU or evicting active suppression.

A separate map owns at most five automatic empty-composer requests until completion (including detached work and retry backoffs). At capacity, new automatic keys remain eligible without a placeholder; a later snapshot or visit can admit them once a slot frees. Chat switches, history loading, editing and ordinary refresh detach the live view without aborting those requests. Returning to the same key attaches to the existing request. Completion writes text even while another chat is open, but displays only for the current matching empty composer. Dismissals and newer explicit results win over older detached completions. Failures write nothing, and a later visit is eligible again. App shutdown, reload/navigation suspension and provider key changes abort relevant requests. One shared view timer also services detached two-second retry backoffs; a transient request gets at most one retry. Turning suggestions off or superseding/dismissing a result prevents an unnecessary detached retry.

The requested-draft map contains one normalized string per conversation, bounded with the 50-conversation fingerprint LRU. A document/chat-lifetime identity handles unidentified conversations. Every continuation dispatch, nonempty-draft dismissal and successful application writes suppression; ready snapshots with empty or meaningfully different drafts clear it. Unready snapshots do not establish draft end. The live slot owns the current operation/instruction, exact composer draft/context, cancellation controller and optional offer or retry notice. Compatible history/focus updates preserve pending work. Compatible connector-key changes republish the current live offer or recovery notice under the new key. Edit activity hides displayed text immediately and keeps live recovery until the next snapshot decides compatibility. Exact draft changes discard offers even when normalized whitespace keeps a recovery request compatible. Navigation/refresh/configuration changes discard the slot, and `clear` hides pending dots and notice popups so a visible Try again always belongs to a replayable live request. Results require the exact draft and latest-message context; live Try again replays the original operation/instruction using the current draft. No result, failure or cancelled-attempt history is retained for written drafts.

Reconfiguration asks for a nonce-tagged fresh snapshot only when effective active output settings change. During suspension it defers that request until document load. Failed conversation-identification acknowledgements consume their nonce; superseded responses and queued old-document snapshots cannot schedule generation. The connector acknowledges a main-owned offer ID only after native insertion returns, before emitting edit activity. Failed insertion stops automatic application, restores the original selection, emits one unsuccessful acknowledgement and retains explicit Try again without successful application suppression. Automatic-send rule changes preserve unrelated inline work and retain all existing main-owned permission checks.

`RequestCounts` wraps actual provider dispatches and aggregates local-day counts in the separate owner-only, atomically replaced `request-counts.json`. It keeps 30 days (at most 10,000 aggregate rows), batches writes at 30 seconds and flushes on quit. It serializes only allowlisted provider/model/method/reason/count fields; aborted and timed-out dispatches remain counted even if the transport settles late. No suggestion keys or private request/response bodies enter telemetry. Model lists use a bounded ten-minute provider/key-hash cache; Refresh models bypasses it and key changes invalidate it.

Suggestion-only direction inference follows explicit message IDs/native markers: consecutive bubbles may inherit the immediately preceding bubble’s direction when aligned on the same side, otherwise clearly left/right-aligned bubbles use pane geometry. Dividers break inheritance and ambiguous/zero-sized bubbles stay unknown. Inferred direction is marked in snapshots and never qualifies automatic sending or sent-style samples; changes in direction authority invalidate full send snapshots without invalidating equivalent inline content. Jumbo emoji alt/data-plain-text is extracted outside text wrappers while excluding quotes, authors, reactions and media labels.

At the five-detached-request cap, Assistant retains only the current eligible candidate and debounces it again when capacity frees. A matching fresh view clears stale awaitingSnapshot on reattachment. Connector acknowledges display acceptance/rejection against a main-owned offer ID/key. Rejection triggers at most three snapshot recovery attempts and reuses valid cached/live text, without another provider request. Dismissal targets the visible offer by ID across display-key updates, or the request ID carried by inline loading dots and request-bound notices. It aborts that work and records its original empty-composer context, including when the current snapshot has already advanced; a different newer offer remains eligible. The connector remembers dismissed offer/request IDs across snapshot recovery and rejects queued results for them. Refresh acknowledgements get three snapshot attempts; after a same-document timeout, the next ordinary snapshot may reconcile the view. Suspended/reloaded documents still require a matching nonce before admission.

The sibling owner-only `suggestion-decisions.json` aggregates day/reason/count for allowlisted admission/lifecycle/display decisions, with the same 30-day retention and flush schedule. Transition tokens and offer associations remain bounded runtime memory; no text, names, message/chat IDs or keys are serialized into these counts.

These controls have focused unit coverage. Electron fixture timing/behavior assertions are updated for CI; no live account/provider checks are claimed for this change.

## Provider model dropdown

Settings loads model options from the selected provider using a validated local-renderer IPC request. The main process obtains the key from the vault and calls fixed HTTPS Models endpoints with redirects disabled and a 15-second total timeout. OpenAI returns its full list; Anthropic follows `has_more` / `last_id` pagination. The result is filtered through `src/core/model-policy.ts`, an explicit catalog of current general-purpose text models checked against the official model pages on September 29, 2026. OpenAI offers GPT-6 Astra, GPT-6.1 Sol, GPT-6 Sol and Luna; Anthropic offers Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 4.5. Only account-returned models are shown. Aliases take priority over duplicate dated snapshots; if no alias is returned, the newest available snapshot is shown. Models with a reported shutdown date, older generations, specialist variants and fine-tunes are excluded. Provider display names are retained. Future model families require updating the policy against current documentation.

Each provider retains its own selection. Refresh, empty catalogs, failures and missing saved IDs never silently change that selection. Saved older/unlisted IDs are shown in a separate notice with a prompt to choose a current model, not offered as dropdown options. Key replacement/removal invalidates outstanding requests, and late results from a previous provider or component are discarded. API keys and provider error bodies never enter the renderer or logs. Restricted keys need Models read permission. No-key, loading, permission, connection, empty-list and retry states appear beside the dropdown. The fixture supplies mixed synthetic catalogs through the same filter with no network access.

Unit coverage includes both provider protocols, pagination, filtering, snapshot deduplication, retired models, old selections, malformed/empty catalogs, safe errors and stale requests. Actual Electron tests cover provider switching, selection retention, refresh, permission-error recovery, missing saved IDs, late responses and displayed model names. The original unfiltered dropdown loaded 138 models from the real OpenAI key after enabling only List models → Read on the dedicated WhatsApp Companion key. The user then requested the current-text-model filter described above. Anthropic discovery has paginated protocol and renderer fixture coverage; no Anthropic key is configured for live verification.

## Reasoning effort

The slider uses the same model policy: GPT-6 Luna/Sol allow `none`, `low`, `medium`, `high`, `xhigh`, `max`; GPT-6.1 Sol, Astra and the current Claude reasoning models start at `low`. Haiku has no effort parameter. Settings are saved per provider and exact model ID. Older state files gain an empty reasoning map on load, preserving other settings and selections. Defaults favor latency (`none` or `low`). The main process validates supported levels, cancels old suggestion/provider-check work when effort changes, and applies the saved effort to suggestions, refinements, automatic-reply preparation and synthetic connection checks. OpenAI uses `reasoning.effort`; Anthropic uses `output_config.effort` without inventing a thinking-disable parameter.

Reasoning counts toward output limits. The bounded output budget is 1,200 tokens at None, 4,096 at Low, 8,192 at Medium, 16,384 at High, and 32,768 at Extra high/Max. Medium and above have a 120-second timeout; lower efforts retain 30 seconds. Cancellation still applies immediately. These are caps, not expected usage or guarantees that a reasoning-heavy request will finish. The UI explains the latency/token tradeoff. Unit tests verify provider payloads, unsupported levels, migration, per-model storage and cancellation; desktop checks exercise mouse/keyboard saving, model switching, non-adjustable models and persistence across restart.

Capability sources: [OpenAI model catalog](https://developers.openai.com/api/docs/models), [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [Sol 6.1](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [Claude model catalog](https://platform.claude.com/docs/en/about-claude/models/overview), and [Claude effort](https://platform.claude.com/docs/en/build-with-claude/effort).

Packaged-app verification confirmed that the configured OpenAI account now displays exactly Astra, Sol and Luna. The slider was visually inspected in the live app, and a synthetic GPT-6 Luna request with Low effort passed. No live contact messages were sent as tests. Higher efforts have protocol/interaction coverage, not a live latency or quality guarantee; Anthropic remains fixture-verified only.

Resolve requires `WAWebCollections.Chat.active()` and `Chat.get(exactWid)` to return the same model, with a factory-round-tripped WID and bounded `formattedTitle`. Main checks title, kind, exact peer ID when present (PN and LID remain distinct), and the unchanged snapshot/destination token, then stores the descriptor in the ticket. Send rechecks the exact active model and visible header before upload, after upload and immediately before invoking `addAndSendMsgToChat` once. A header mutation while awaiting upload revokes the destination even if it switches back. Main grants no second attempt; timeout/exception after dispatch is unknown unless the page explicitly proves no send was invoked. A page deadline prevents a delayed upload/key operation from starting a send after main’s outcome timeout.

The send fields and upload call follow the proven spike and the sticker path in [whatsapp-web.js Utils.js at 064a3d5a5a3dce1281a6a12740b5a7051339d154](https://github.com/pedroslopez/whatsapp-web.js/blob/064a3d5a5a3dce1281a6a12740b5a7051339d154/src/util/Injected/Utils.js), with animation restoration researched against [wa-js at 4b24c7c1e9538c41a6c3db78b49a73650d87924c](https://github.com/wppconnect-team/wa-js/tree/4b24c7c1e9538c41a6c3db78b49a73650d87924c). These are adapted application code, not an imported library. Required module exports are checked on both phases; a `direct-v1:active-get:upload-qpl:key:ephemeral:send-tuple|<WhatsApp version>` fingerprint must stay unchanged. WhatsApp updates may change the shapes or behavior; unofficial internals carry account risk. Success requires the returned registered model’s exact key, sticker type, destination and ack ≥ 1. This is acknowledgement, not proof the recipient read the message.

Explicit unavailable results (missing modules, unsupported shapes/version, or unresolvable chat) can release the direct grant and resume the existing maker/picker policy under the same still-valid ticket only before any upload/send. Destination changes, invalid results and uncertain attempts terminate without fallback. `uploaded` in the internal result means the upload operation was invoked, even if it rejected; it prohibits fallback. Main bounds resolve to 3 s and the send result to 30 s; upload has a 20 s abort signal and the page checks a 25 s deadline before send. Turning the setting off prevents new direct attempts and revokes pending resolution; an already dispatched attempt remains consumed.

Main keeps an in-memory rolling budget of at most 10 page-side send invocations per 60 seconds, consumed immediately before executing the send phase (including failed/unavailable calls). Resolve and native sends consume no budget. At the cap, the same still-valid ticket immediately follows its normal maker/picker draft policy, without a queue or delay, and records `route: direct`, `outcome: fallback`, `code: rate-limit`. Turning the toggle off/on does not reset the budget.

The isolated connector emits a strict `accountSafety` event containing only `logged-out`, `account-warning`, or null. Visible QR/link-device/login structural markers identify logout; visible dialogs/banners plus allowlisted English, Spanish or Portuguese restriction phrases identify account warnings. Hidden content, message bodies and composer text are excluded; QR values, notice text and account details never cross IPC. Main disables direct mode and persists optional validated global `directStickerDisabledReason` and `directStickerDisabledAt` fields on either signal while enabled. Main also stops on errors/unknown outcomes after invoking the send phase (`send-error`), or on `module-shape` failures after any successful direct send in the app session (`whatsapp-changed`). A pre-success, pre-upload shape failure still falls back. Expected destination changes do not trigger a safety stop; uncertain attempts remain consumed and never retry. The first stop reason remains until re-enable. Settings shows one short hint below the off toggle. The user can resolve the issue and turn the toggle on to clear both fields; a still-visible warning/login screen immediately stops it again. Account risk remains despite these guards.

The shared owner-only, rotating diagnostics writer also appends validated structural direct-route phase/timing/outcome/failure-code/fingerprint records to `diagnostics/sticker-sends.log`. Records contain no chat IDs, nonces, hashes, names, image bytes or raw errors. The fixture supplies a fake main-world `window.require` set, with upload/send/missing-module/delay/failure controls and local outgoing sticker rendering. Unit coverage executes the serialized function against that fixture, checks original bytes and drafts, and exercises exact LID/group destinations, changed chats, pre-upload fallback, argument/result bounds, nonce/attempt latches, deadlines, the rolling cap, reason persistence, account-safety signals and the kill switch. Desktop fixture scenarios cover cap fallback, QR/logout and account-warning stops. Build/unit checks run in this worker; Electron fixture and live compatibility checks remain with the orchestrator.

## Sticker rediscovery and perceptual suppression

`forgottenStickers` is a globally scoped, main-owned list in `companion.json`. Forget atomically removes the library entry and records its exact SHA-256, then discards pending intake for that hash. Intake checks the list both before queuing and immediately before committing. The most recently forgotten 5,000 unique hashes are retained; oldest hashes are dropped. The optional schema field defaults to an empty list for older stores. Forgetting a re-encoded duplicate does not deny its original, and there is no restore UI.

SHA-256 remains the identity used for stored images and sending. A new hash is compared with existing library entries using an optional versioned first-frame fingerprint: a 64-bit horizontal dHash over a 9×8 RGB thumbnail, composited over white. Main verifies the bounded RIFF/WebP bytes against SHA-256, detects animation only by walking ANIM chunks, and checks canvas/frame dimensions before decoding (at most 2,048×2,048 for fingerprinting). The fixed bundled decoder runs in an isolated world of the trusted local controls renderer using `createImageBitmap` and `OffscreenCanvas`. Only main-supplied stored bytes enter that decoder, and main validates the returned 216 RGB bytes and computes the hash itself. WhatsApp cannot supply a fingerprint or access an additional API. This reuses Chromium's decoder without a native runtime dependency or a remote-page bridge.

Suppression requires Hamming distance ≤4/64 and thumbnail mean absolute RGB difference ≤12/255. Static observations can match either static entries or the first frame of animated entries: the latter suppresses flattened copies made by WhatsApp's sticker maker or GIF flattening. Animated observations can match only animated entries, so a static entry never suppresses an incoming animation. Four differing bits permit small re-encoding artifacts while keeping the visual comparison conservative; the color check avoids dHash collisions between flat fills or similar gradients. A match updates only the existing entry's `lastSeen`, preserving its bytes, identity and search terms. No existing entries are removed or merged. This is approximate: crops, large encoding changes and decoder failures can escape suppression, while images that differ only in details below thumbnail resolution can match. Animated stickers are compared by first frame only, so distinct animations with matching first frames may match. Oversized-dimension or undecodable images retain exact-hash indexing only, within the 1 MiB-per-sticker/2,000-entry/1 GiB-live-blob limits.

Existing fingerprints migrate lazily when a new image needs comparison, without decoding at startup. Decoding is serial and asynchronous, with a two-second deadline per renderer decode; migrations share the intake batch's atomic save. Fingerprints and decode failures remain cached for surviving library entries across completed batches, and are invalidated on Forget or when the image no longer survives. Each batch uses the latest store state after decoding, preserving intervening Forget/search-term/settings actions. Pending intake is bounded by the existing library limits of 2,000 images / 50 MB. This replaces the previous synchronous 5 MB flush threshold so a discovery burst is retained while asynchronous legacy decoding runs; observations beyond those bounds are dropped. Shutdown stops intake and allows at most three seconds for decoding and normal draining. At that deadline, main cancels its decode wait and atomically persists all remaining observations using exact hashes only, without adding fingerprints or migrations. Late renderer results cannot change the saved library. Save failures are reported and do not leave Close/Quit waiting for decoding.

Regression coverage uses generated synthetic WebPs at two quality settings plus different-content and animated variants. Unit tests use independently decoded first-frame thumbnails from Pillow (the generation script is beside the fixtures, and Pillow is not a runtime/test dependency), plus a mirrored thumbnail to check different content with identical colors. Tests cover flattened-static suppression against stored and same-batch animations, preservation of incoming animations, decode deadlines, shutdown fallback/late results/save failures, cache retention and eviction, exact-hash isolation, the bounded persisted denylist, backward-compatible schemas, lazy fingerprint migration, decoder-output validation and Forget during an in-flight decode. Existing desktop scenarios exercise the actual trusted canvas decoder, re-encoded suppression, preservation of animated observations against static entries, and Forget → reobserve → actual restart → reobserve. The new shutdown and flattened-copy behavior has unit coverage; Electron verification remains with the orchestrator.

## Content-addressed sticker storage (schema v2)

The previous library could silently refuse intake at its 50,000,000-character encoded-image budget. `companion.json` now contains only hash IDs, first/last-seen timestamps, search terms, optional fingerprints, WebP kind and byte size. `stickers/<sha256>.webp` contains unchanged bytes in an owner-only directory. The library allows 2,000 entries and 1 GiB of live blob bytes, excluding backups and temporary files; pending observations have an independent 50,000,000-character/2,000-entry bound. Capacity and disk errors use the existing Stickers hint line. Intake handles blob failures per sticker: invalid bytes, damaged existing blobs and over-budget observations are dropped without blocking valid additions or changing damaged entries/files. IO failures retain pending observations and report "Couldn't save new stickers", with exponential backoff and at most five automatic attempts per hash. Exhausted observations remain pending within intake bounds; an explicit flush can retry them. Shutdown also drains fresh observations queued behind a failed batch. Startup GC skips failed orphan deletions, continues with other orphans, and never prevents opening an otherwise valid manifest.

Startup explicitly validates v1 metadata and every inline WebP before creating a non-overwritten `companion.v1-backup.json`. It durably writes/re-verifies every blob (including reused files), then atomically replaces the manifest with v2. File fsync and Linux directory fsync order the backup, blob and manifest updates. Replacement is the save boundary: later directory sync failures return success, adopt saved state and allow normal reconfiguration/invalidation, while logging a durability warning and retrying directory sync on the next write. This also applies to credentials and picker diagnostics. Failures before replacement throw without changing live state. Fault-injection checkpoints cover write, file sync, rename, directory sync and verification boundaries. An interrupted migration leaves v1 intact or v2 complete; rerunning finishes without re-encoding or deduplication. Existing corrupt files stop migration rather than silently replacing evidence. Missing/corrupt v2 files preserve metadata and fail closed until the file is restored or the app rediscovers the exact-hash sticker and repairs it. Backups and restoration must include the manifest and its stickers folder; restoring the v1 backup loses changes since migration.

Controls uses its own nonpersistent `companion-controls` partition. Only that session registers the `companion-sticker` handler; scheme privileges are registered before readiness and do not bypass CSP. Requests require a canonical current hash and re-verified, regular, bounded WebP bytes, with no-store caching. The controls CSP permits the scheme only for images. The `persist:whatsapp` session (and disposable fixture session) cannot load it through image, fetch or navigation. Cards and shield art use protocol URLs; cards load lazily and offer a recoverable Retry state. Fingerprinting receives verified bytes in the trusted isolated renderer. Maker, picker, direct sends and Locate verify stored files; async direct resolution and native preparation recheck current membership/bytes/authorization before use. Synchronous manifest/blob mutations serialize; Forget durably removes metadata and records the tombstone before unlink. GC runs only after successful manifest validation/migration, and defers removal of recognized unreferenced files until after remote navigation starts. An absent manifest also skips GC because there is no authoritative reference set. Existing blob IDs are recorded in `sticker-recovery.json` and excluded from later GC, including after unrelated saves and restarts; the Stickers hint recommends restoring `companion.json` or its v1 backup. A loaded restored manifest or a successful save after rediscovering all preserved IDs clears the recovery hint. The record remains until the replacement manifest’s directory sync succeeds, so a durability warning cannot remove the crash-recovery guard. Cleanup failure is non-blocking and retries on the next write.

Build and unit verification are run by the implementation worker. Added Electron scenarios cover schema-v1 startup migration, protocol isolation and missing-file recovery; Electron execution is left to the orchestrator.

## Confirmed sticker deletion

Edit mode exposes a bottom-bar trash action beside the selected count and Groups. The editor uses the same trash icon. Both replace their action row with an inline Delete/Keep question, initially focusing Keep; Escape dismisses it before other panel actions. Delete/Backspace on a focused edit-mode tile opens the bar question, temporarily selecting that tile if needed. Keep/Escape restores its focus and removes only that temporary selection. Selection changes dismiss the question; selections otherwise survive filters. Successful deletion clears its original selection only if no subsequent selection or group-control interaction occurred, preserves newer editors and popovers, announces the deleted count, and focuses the tile at the first deleted position, then the last remaining tile or Search.

Main validates `forgetStickers {ids}` as 1–2,000 unique SHA-256 hashes. Single and bulk actions share store mutation and per-id cleanup; unknown hashes are ignored. A bulk request removes all known references and records all tombstones in one manifest update, invalidates file caches, then unlinks blobs after crash durability is confirmed. Failed manifest writes leave all references and blobs intact. Failed blob deletion is non-blocking and continues with the other ids, leaving tombstoned orphans for startup GC. The store returns only the IDs actually removed or tombstoned, including preserved recovery blobs. Both actions discard pending intake/fingerprint caches and clear affected image errors only for those IDs; ignored unknown IDs leave pending discovery untouched. They cancel affected transfers before authorization, including prepared picker transfers, while already-granted sends finish. Directory sync warnings appear in the existing library status banner (alongside the deletion announcement) and clear after a later successful sync.

Unsaved search-term drafts survive search/group filtering, membership changes, group edits/removal, and virtualization. Editor Close, clicking the same tile, switching editors, Done, and Escape leaving the editor or edit mode all use the same Keep editing/Discard guard. Panel Back/Close, App-level panel Escape, the AI-settings link, rail navigation (including toggling the active sticker rail button closed), and application-menu navigation also use that guard. Main requests rail/menu navigation through a validated local-controls IPC subscription before changing the panel; the remote WhatsApp page receives no new API. A hidden draft's prompt renders in a detached editor row and scrolls into view; Keep editing clears hiding search/group filters and focuses the retained text. Repeated Escape keeps the draft and cannot close the panel without explicit discard. Hidden delete questions may disappear silently, but never discard text. Single, selected, and keyboard deletion explicitly warn when they will discard an affected draft; successful confirmed deletion clears only deleted drafts, while failed deletion and deletion of other stickers retain them. Older Save acknowledgements cannot close a newer discard prompt.

## Startup reliability

The isolated remote preload installs a capture-phase resource-error listener before requesting a boot session from main at document start. It retains only the first failed script/stylesheet kind, including script/style preloads and modulepreloads, and reports it in heartbeats; failures after shell/login/blocked recognition are ignored. Electron's [isolated context](https://www.electronjs.org/docs/latest/api/structures/web-preferences) uses Chrome's isolated worlds, which [share the page DOM](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts#communication); the listener needs no bridge. Main binds the request and every heartbeat to the remote main frame/origin, a fresh nonce and navigation generation. A timer samples only fixed structural selectors and numeric progress attributes every two seconds. The full DOM connector starts once per document immediately on shell, login, blocked or unknown phases, once the document body exists. Only a recognized splash defers activation, with a 20-second deadline from detector start; expiration is recorded as `connector-deferral-expired` in startup diagnostics. Login and blocked activation preserves the existing account-safety checks. Timer heartbeats continue after activation. Shell detection does not depend on `snapshot.ready` or an open conversation. Markup drift falls back to unknown, activates the connector and cannot trigger splash recovery. These selectors still require verification against current live WhatsApp markup.

Mutation callbacks filter Companion-owned and irrelevant changes before invalidation. Each callback handles at most 200 records and 512 changed nodes/descendants/ancestors. Exhaustion resets the message cache and schedules a coalesced refresh so detached/recycled bubbles remain correct. No unbounded descendant list is materialized.

The main watchdog uses monotonic receipt times. For ordinary recovery, gaps over six seconds, hidden/offline observations and busy/closing gates reset its observation grace period. Confirmed splash duration must reach 60 seconds and unchanged phase/progress must reach 30 seconds. A failed startup script or stylesheet enables recovery after five seconds of unchanged splash progress, including while the window or page is hidden. Offline, busy/closing gates, heartbeat gaps and progress changes restart this confirmation. Two ordinary `webContents.reload()` calls are allowed per launch, with no initial delay and at least 120 seconds between reloads; the budget survives navigation and manual reload. No storage clearing or automatic logout is performed. Initial remote web preferences disable background throttling; first shell detection restores it once. Zero/nonfinite layout sizes are rejected and logged, with the last valid remote bounds retained.

A separate main-process load recovery handles failed or uncommitted navigations, including while hidden. Non-aborted main-frame load failures retry `loadURL(remoteURL)` after 2/5/15/30 seconds, then every 60 seconds indefinitely. A successful HTTP commit (2xx/3xx), or dom-ready without a preceding navigation failure, resets backoff. New main-frame navigation cancels pending retries. Cross-document navigation without commit, failure or dom-ready for 45 seconds triggers stop plus reload; a second stall relaunches once through normal shutdown, preserving runtime/data-directory arguments and using the AppImage executable when applicable. A visible window drops `--hidden`. The `--relaunched-after-stall` marker prevents another relaunch; persistent stalls then stop/reload every 60 seconds after the initial 45-second timeout. Closing cancels both timers. Recovery diagnostics contain only bounded numeric error codes and attempt counts (`load-failed`, `load-retry`, `navigation-stalled`, `relaunch`).

While running, local startup page load rejections record `base-load-failed` or `controls-load-failed` with only a bounded numeric error code when available, and do not abort remote startup. Controls retry once if their URL has not committed; `controls-loaded` follows the attempts only when the controls URL is present. Once closing begins, pending startup loads stop quietly without retries, failure diagnostics or a startup error dialog. Startup diagnostics use an allowlist, an ordered asynchronous writer, a 512-record pending limit, a 256 KiB file limit and one rotated predecessor. Directory/file permissions are 0700/0600. Each launch appends a distinct local timeline, with wall-clock and monotonic timestamps. A one-time signature reports whether visible progress exists, its tag and up to three ancestor tags. It is emitted immediately for visible progress or a known splash marker; otherwise it waits for document completion and the existing unknown grace condition, preserving the snapshot through an initial empty document. Tags use an explicit standard HTML/SVG enum shared with main validation, with custom or unrecognized tags reported as `other`. Ancestor IDs and test IDs use the explicit structural-identifier enum shared with main validation; other attribute values become `other`, absent attributes become null, and booleans record attribute presence. Account-derived identifiers and token-shaped attributes cannot enter the log. Progress is read within a known splash container when present; document-wide progress is used only without a known splash, after shell/login/blocked checks. Renderer failure diagnostics record fixed reasons only. No page text, URLs or exception messages enter the log. Shutdown marks closing before cancellation; all renderer sends check webContents and frame destruction and catch disposal races. Idempotent cleanup isolates failed steps, drains intake, closes views and allows at most one second for diagnostic flush before quitting. Second-instance activation is ignored while closing.

The disposable desktop fixture supports `--fixture-startup-splash` (splash then shell), `--fixture-startup-watchdog` (stuck splash) and `--fixture-startup-asset-failure` (stuck splash with a missing local stylesheet). The latter two select fixed shortened main-only thresholds (600 ms splash, 300 ms stalled/asset failure, 1200 ms spacing); they are accepted only with `--fixture` in an unpackaged app. Production and normal fixture thresholds remain 60/30/5/120 seconds. `--fixture-startup-stall` holds the first navigation in a fixture-only nonresponding protocol handler, then retries into the shell with fixed 1500/2000 ms stall thresholds and 200/500/1000 ms failure backoff; it also requires an unpackaged fixture. The page receives no privileged bridge or configuration API. Focused startup tests cover classification, deferral, mutation budgets, watchdog gates/authentication, frame disposal and diagnostics privacy/rotation. The CI desktop fixture verifies delayed activation, throttling, automatic reload budget, isolated-world resource-error capture while hidden, uncommitted-navigation recovery while hidden and shutdown after remote disposal.
